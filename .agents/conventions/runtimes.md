# Runtimes

> [!info] When to load
> Load when tagging tasks in `breakdown-tasks` (`[I]` / `[A]` / `[*]`) or deciding how to execute `implement` across sessions. Prerequisites: `AGENTS.md`.

## Runtime markers in `tasks.md`

Every task generated by `breakdown-tasks` carries a runtime modality marker:

| Marker | Meaning | Best for |
|---|---|---|
| `[A]` | **Autonomous** | Mechanical or backend tasks with deterministic tests (models, schemas, controllers, routes, events, CLI scripts, unit/integration tests) |
| `[I]` | **Interactive** | Tasks requiring human-in-the-loop visual, UX, accessibility (WCAG), or product judgment |
| `[*]` | **Either** | Tasks executable in either interactive IDE or headless/autonomous sessions |

## Clean-context primitive (for `implement`)

`implement` is **agent-agnostic**: the conversation is disposable, and **the repository is the memory** (`tasks.md` checkboxes `[x]` + Git commits). Each task is a **cold start** using the runtime's native clean-context primitive:

| Modality | Clean-context primitive |
|---|---|
| Interactive IDE / Desktop | A **new chat / session** per task or repo group (`/clear` or new chat) when context grows; `/compact` only to continue the same task |
| Autonomous CLI / Headless | **One run per task** or repo group |
| Subagent-capable runtime | An isolated **subagent** per task or repo group |

Within a single repository, run tasks **sequentially** on a standard Git branch (`git-conventions`, each verified by tests + juez and committed before starting the next). Across independent repositories, repo groups (`--repo <id>`) may run **in parallel** in separate clean contexts because their cross-repo contracts (`api.md`, `event.md`) are already pinned by `plan-feature`. Creating a `git worktree` is optional and needed only when running two concurrent autonomous agents on the **same** local repository checkout.

### Selective loop execution (`ralph-loop` / CLI runner)

When multiple tasks are pending in `tasks.md`, `implement` supports running either interactively in the IDE or through an external clean-context loop script (`.sh`) with explicit scope selectors:

- `--repo <repo-id>`: execute only the unchecked tasks under `### <repo-id>`.
- `--tasks T01,T02` (or range `T01..T03`): execute only the specified task IDs, one fresh session per task.
- `--only-autonomous`: execute `[A]` (and `[*]` unless restricted) tasks automatically and pause whenever an `[I]` (interactive) task is reached or the 2-attempt circuit breaker triggers.
- Model capability (`low` / `med` / `high`) is passed directly by the loop runner per task without spending an agent iteration editing `.env` files.

### Instinct-based continuous learning (project vs global scope)

To prevent context bloat from one-off session notes, recurring lessons or pitfalls discovered during `implement` are recorded first as atomic **instincts** (`confidence: 0.3–0.9`, `scope: project | global`). A pattern is promoted into a durable repository rule or `SKILL.md` only after **>= 2 observed occurrences** with concrete evidence (`confidence >= 0.7`), and promoted to the global kit only when validated across **>= 2 repositories**.

## Mapping skills to runtimes

| Skill | Typical runtime | Why |
|---|---|---|
| `drill-docs` | Interactive (`[I]`) | Dialogue-driven extraction (one question at a time) |
| `save-output` | Interactive (`[I]`) | Confirms type, path, and split decisions with the human |
| `judge-spec` | Interactive (`[I]`) | Iterative human clarification and explicit approval |
| `plan-feature` | Interactive (`[I]`) | Interrogate loop + mutual-understanding checkpoint |
| `breakdown-tasks` | Interactive or Autonomous (`[*]`) | Mechanical once the plan and companions are complete |
| `implement` | Agnostic (`[*]`) | Cold-start per task; state lives in `tasks.md` + commits |
| `close-spec` | Interactive (`[I]`) | Notary verification + explicit human sign-off |
